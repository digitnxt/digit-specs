SUMMARY 
-----------------------------------

Service: account
- 3.0 introduces a standalone Account Management API with `/account/v1` and `/account/v1/{id}` plus `/account/v1/config` endpoints, implying account entities and configurable account behavior are now first-class.
- 2.9 doesn’t have an Account spec; the closest is User Service, which focuses on citizen/user/profile/password flows, so account data is likely split from user identity concerns.
- Expect new account-specific schemas and request/response payloads that don’t map 1:1 to User Service structures.

Service: billing-payment
- 3.0 exposes resource-style endpoints for business services, tax heads, demands, bills, and payments under simpler paths like `/business-services`, `/tax-heads`, `/demands`, `/bills`, `/payments`.
- 2.9 splits this across Billing Service, Collection Management, and Payment Gateway with older prefixed routes (`/billing-service/...`, `/payments/...`, `/pg-service/...`).
- Expect consolidation and path normalization, plus schema changes due to merging of billing and payment concerns in one spec.

Service: boundary
- 3.0 shifts to top-level operations (`/_create`, `/_search`, `/_update`) and keeps hierarchy-definition and boundary-relationships, plus a shapefile boundary create endpoint.
- 2.9 Boundary V2 namespaces these under `/boundary/...` which means clients must update base paths.
- Core concepts remain similar; biggest change is URL structure and likely request wrapper schemas.

Service: common
- 3.0 Common spec is purely shared schemas and appears slimmer than 2.9 Common Object Definitions.
- This implies shared types were renamed/removed or moved to service-specific specs.

Service: filestore
- 3.0 introduces a multi-step upload lifecycle: request upload, confirm upload, fetch download URLs, and document categories.
- 2.9 Filestore had `/files`, `/files/url`, `/files/metaData`, `/files/id` style endpoints with a more direct upload model.
- Expect flow changes for clients: more steps and possibly pre-signed upload URL handling.

Service: idgen
- 3.0 adds template management with `/v1/template`, and generation via `/v1/generate`.
- 2.9 has a single `/id/_generate` endpoint.
- This indicates template-driven IDs are now explicit, with a versioned path format.

Service: individual
- 3.0 introduces an Individual Service (`/v1`, `/v1/{id}`, `/v1/bulk`, `/health`) focused on managing person/entity records.
- 2.9’s closest spec is User Service, but it mixes identity/auth flows with user profile management.
- Expect a separation of concerns: Individuals as domain entities vs users as auth/actor identities.

Service: localization
- 3.0 defines `/messages`, `/messages/_upsert`, `/messages/_missing`, `/cache/_bust`.
- 2.9 (derived from Postman) uses `/messages/v1/_search`, `_create`, `_update`, `_upsert`, `_delete`, `_missing`, and `/cache/v1/_bust`.
- 3.0 drops `_delete` and removes explicit `/v1` in the path; semantics remain similar but clients must update routing and possibly request bodies.

Service: mdms
- 3.0 combines MDMS v1/v2 into a single spec and adds explicit `/schemas` and `/data` resources.
- 2.9 has separate `mdms.yaml` and `mdms-v2.yaml`, mostly focused on search/create/update routes.
- 3.0 adds clearer schema lifecycle and data lifecycle APIs, suggesting more structured MDMS usage.

Service: notification
- 3.0 is template-centric and channel-centric: create templates, preview templates, send email, send SMS.
- 2.9 User Event service is event-centric: create/update/search events and count notifications.
- This is more than a rename: it’s a shift from event-driven notifications to explicit template and channel APIs.

Service: otp
- 3.0 uses `/v3/otp/generate`, `/resend`, `/verify`, `/invalidate`.
- 2.9 uses `/otp/v1/_create`, `/_validate`, `/_search`.
- 3.0 expands capabilities (resend/invalidate) and standardizes naming.

Service: workflow
- 3.0 exposes detailed primitives for process/state/action and escalation/transition, all versioned under `/v1/...`.
- 2.9 focuses on process transition/search/count and businessservice CRUD under shorter paths.
- 3.0 is more granular and likely requires client changes to call new endpoints for workflow definition and state/action management.
