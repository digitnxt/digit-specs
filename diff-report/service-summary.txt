SUMMARY (service-by-service)
----------------------------------

Service: account
Summary: The 3.0 spec introduces a dedicated Account Management API under `/account/v1` with CRUD-style endpoints and config endpoints. In 2.9, the closest spec is User Service with citizen/user/profile/password flows, so functionality is reorganized rather than a direct path upgrade. Expect account to be split out from user-centric APIs, with different schemas and request/response models.

Service: billing-payment
Summary: 3.0 consolidates billing-related workflows into a single Billing - Business Service API with resources like `/business-services`, `/tax-heads`, `/demands`, `/bills`, and `/payments`. In 2.9, these concerns are spread across Billing Service, Collection Management, and Payment Gateway. The 3.0 surface is more resource-oriented and appears to reduce legacy path prefixes while covering business services, demand, bill generation/cancel, and payment recording in a unified API.

Service: boundary
Summary: 3.0 presents boundary operations at top-level paths like `/_create`, `/_search`, and `/_update`, plus hierarchy-definition and boundary-relationship endpoints and a shapefile upload path. In 2.9, Boundary V2 namespaces these under `/boundary/...`. The functionality is similar, but routing and path structure have shifted (likely to simplify or standardize).

Service: common
Summary: 3.0’s Common API specification is a reduced set of shared schemas compared to 2.9’s Common Object Definitions. This indicates a cleanup/realignment of shared models rather than new endpoints (no paths in either spec). Expect fewer or renamed shared schema definitions.

Service: filestore
Summary: 3.0 moves to a document-oriented upload flow with `/upload`, `/upload-url`, `/confirm-upload`, and `/download-urls`, plus document categories. The 2.9 Filestore uses `/files` and related URL/metadata endpoints. The 3.0 API suggests a multi-step upload process and categorization not present in 2.9.

Service: idgen
Summary: 3.0 uses `/v1/template` and `/v1/generate` for ID generation, while 2.9 exposes a single `/id/_generate`. The functionality remains similar but is expanded to include templates and a clearer versioned route structure.

Service: individual
Summary: 3.0 introduces an Individual service with `/v1` CRUD-style endpoints and `/v1/bulk`, plus `/health`. In 2.9, the closest counterpart is User Service (citizen/user/profile). This indicates a domain split: individual entity management separated from user authentication/identity services.

Service: localization
Summary: 3.0 defines `/messages`, `/messages/_upsert`, `/messages/_missing`, and `/cache/_bust`. The 2.9 spec is derived from the Postman collection and uses `/messages/v1/_search`, `/messages/v1/_create`, `/messages/v1/_update`, `/messages/v1/_upsert`, `/messages/v1/_delete`, `/messages/v1/_missing`, and `/cache/v1/_bust`. The 3.0 spec drops `_delete` and standardizes paths (version segment removed) while keeping core message CRUD and cache bust semantics.

Service: mdms
Summary: 3.0 MDMS expands schema and data management with `/schemas` and `/data` endpoints, in addition to existing MDMS v1/v2 search and create/update routes. 2.9 splits MDMS into v1 and v2 specs; 3.0 consolidates and adds explicit schema/data resources for a more structured data lifecycle.

Service: notification
Summary: 3.0 provides explicit template creation/preview and direct email/SMS send endpoints. 2.9’s User Event service focuses on event creation/search/update and notification counts. This reflects a shift from event-based notifications to a dedicated notification API with template management and channel send actions.

Service: otp
Summary: 3.0 OTP APIs are namespaced as `/v3/otp/*` with generate/resend/verify/invalidate. 2.9 uses `/otp/v1/_create`, `/_validate`, and `/_search`. The 3.0 API adds resend and invalidate as first-class operations and changes path structure.

Service: workflow
Summary: 3.0 exposes detailed process/state/action endpoints under `/v1/process`, `/v1/state`, `/v1/action`, and escalation/transition operations. 2.9 provides process transition/search/count and businessservice CRUD under `/process` and `/businessservice`. The 3.0 spec appears to move toward more granular workflow primitives and a versioned, more REST-like model.
