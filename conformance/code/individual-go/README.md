# Individual Service

Tenant-aware registry of natural persons (citizens, beneficiaries, staff)
for the DIGIT v3 platform. REST CRUD, paged search, optimistic concurrency,
soft delete, per-tenant validation config, and vault-backed PII encryption.

Schema-separated: each tenant gets its own PostgreSQL schema; the
`tenantdb.GinMiddleware` switches `search_path` per request.

---

## Base path

| Environment | Base URL |
|---|---|
| Local (port-forwarded) | `http://localhost:8080/individuals/v3` |
| LTS (Kong gateway)     | `https://digit-lts.digit.org/individuals/v3` |
| Configurable via       | `SERVER_CONTEXT_PATH` (default `/individuals/v3`) |

---

## API surface

### Individuals (tenant-scoped)

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/individuals` | Create an individual. Returns `201` with the full DTO + `Location` header. |
| `GET`  | `/individuals` | Search. Filters: `id`, `individualId`, `givenName`, `mobileNumber`, `gender`, `dateOfBirth`, `includeDeleted`. Paginated by `page` (≥1) / `size` (1–100). |
| `GET`  | `/individuals/exists` | Existence check by any single filter — returns `{"exists": true|false}`. |
| `GET`  | `/individuals/{id}` | Get one. |
| `PUT`  | `/individuals/{id}` | Full replace. Carries optimistic-lock `version`. |
| `DELETE` | `/individuals/{id}` | Soft delete. Returns `204`. |

### Tenant validation config

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/configs` | Upsert the per-tenant validation config (mobileRegex / nameRegex / uniquenessCriteria). At least one must be present. |
| `GET`  | `/configs` | Get the current config. `404` if none set. |

### Operational

| Method | Path | Purpose |
|---|---|---|
| `GET`  | `/health` | Liveness probe. No tenant header required. |
| `POST` | `/internal/migrate` | Trigger tenant-aware migration. Only when `SCHEMA_SEPARATION_MODE=true`. |

## Headers contract

| Header | Required | Notes |
|---|---|---|
| `X-Tenant-ID` | Required | Drives the search_path switch. Kong injects this. |
| `X-User-ID` | Required on writes | Audit-author. No `system` fallback. |
| `Content-Type: application/json` | Required on POST / PUT | |
| `X-Request-ID` | Optional | Generated by the service if absent. |
| `Authorization: Bearer <token>` | Validated by Kong | The service trusts the gateway. |

## Error envelope

Every non-2xx response is a JSON array of error objects:

```json
[
  {
    "code":        "VALIDATION_ERROR",
    "message":     "Validation failed",
    "description": "One or more validation checks failed",
    "params":      { "field": "mobileNumber", "message": "mobileNumber must be 6-15 digits", "value": "abc" }
  }
]
```

| Status | Code | When |
|---|---|---|
| `400` | `VALIDATION_ERROR` | Field, format, or business rule failure. |
| `400` | `INVALID_REQUEST` | Body parse / unknown field. |
| `404` | `NOT_FOUND` | Individual not present. |
| `409` | `UNIQUE_ENTITY_ERROR` | `mobileNumber` already exists for this tenant. |
| `409` | `ROW_VERSION_MISMATCH` | PUT with stale `version`. |
| `500` | `DATABASE_ERROR` / `INTERNAL_ERROR` | Server-side failure. |

## Validation rules (baseline)

- `givenName` — required, ≤128 chars, alphabets and spaces only.
- `familyName` — ≤128 chars, alphabets and spaces only.
- `gender` — required, one of `MALE`, `FEMALE`, `OTHER`.
- `mobileNumber` — digits only, 6–15 chars; unique per tenant; tenant `mobileRegex`
  (set via `POST /configs`) can override.
- `email` — RFC-ish, ≤254 chars.
- `dateOfBirth` — accepts both `YYYY-MM-DD` and full RFC3339; must not be in
  the future and not more than 150 years in the past.
- At least one of `mobileNumber` or `email` must be supplied.
- `address` ≤ 16 entries, `identifiers` ≤ 16, `documents` ≤ 20.

Tenant-config can further constrain via `mobileRegex`, `nameRegex`, and
`uniquenessCriteria` (e.g. `["mobileNumber", "name"]`).

## Example: create

```bash
curl -sS -X POST 'https://digit-lts.digit.org/individuals/v3/individuals' \
  -H 'X-Tenant-ID: pg' \
  -H 'X-User-ID: 00000000-0000-0000-0000-000000000001' \
  -H 'Content-Type: application/json' \
  -d '{
    "givenName":    "Aisha",
    "familyName":   "Khan",
    "gender":       "FEMALE",
    "mobileNumber": "9876543210",
    "email":        "aisha@example.com",
    "dateOfBirth":  "1990-01-15",
    "identifiers": [
      { "identifierType": "PAN", "identifierId": "ABCDE1234F" }
    ]
  }'
```

## Example: search

```bash
curl -sS 'https://digit-lts.digit.org/individuals/v3/individuals?givenName=Aisha&gender=FEMALE&page=1&size=20' \
  -H 'X-Tenant-ID: pg' \
  -H 'X-User-ID: 00000000-0000-0000-0000-000000000001'
```

## Example: update with optimistic lock

```bash
curl -sS -X PUT 'https://digit-lts.digit.org/individuals/v3/individuals/'"$INDIVIDUAL_ID" \
  -H 'X-Tenant-ID: pg' \
  -H 'X-User-ID: 00000000-0000-0000-0000-000000000001' \
  -H 'Content-Type: application/json' \
  -d '{
    "givenName": "Aisha",
    "familyName": "KhanUpdated",
    "gender": "FEMALE",
    "mobileNumber": "9876543210",
    "dateOfBirth": "1990-01-15",
    "version": 1
  }'
```

Stale `version` returns `409 ROW_VERSION_MISMATCH`. The PUT response carries
the full record (identifiers / addresses / documents are preserved even if
omitted from the body).

## Local development

```bash
# Apply the public-schema (control) migrations
./db/migrate.sh up

# Run
go run ./cmd/server

# Hit it
curl http://localhost:8080/health
```

For per-tenant schema testing locally, set `SCHEMA_SEPARATION_MODE=true` and
either publish a tenant-create event or call `POST /internal/migrate`
directly with `{"tenantId":"pg"}`.

## Schema migrations

- **Control plane** — `db/migrations/` runs once against the public schema
  on startup (one-off `./db/migrate.sh up`).
- **Per-tenant** — when `SCHEMA_SEPARATION_MODE=true`, the service subscribes
  to the account service's `tenant-create` event and runs the same migration
  set against the per-tenant schema.
- **Manual trigger** — `POST /internal/migrate {"tenantId":"<tenant>"}` for
  debugging or back-filling.

The `tenantdb` middleware sets `search_path` on every API request and wraps
it in a transaction; the repos call `r.db.WithContext(ctx)` and pick up the
correct schema automatically.

## Related services

- **Account** — upstream source of `tenant-create` events.
- **AccessControl** — RBAC rules that govern who can hit which endpoint.
- **Vault** (optional) — PII encryption keys for `email`, `mobileNumber`.
